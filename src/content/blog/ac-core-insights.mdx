When a system has weather, locations, elevation, and reports from different times, it is tempting to describe it as smarter than it really is. Two reports are close together, so they must describe the same incident. It is raining near a report, so the situation must be dangerous. A nearby point is lower, so water must be moving toward it.

Each conclusion goes beyond the observation. The data may be useful without proving the stronger claim. I kept running into that distinction while working on AC-CORE, a civic-tech academic team project developed with MMPA Works. I worked on the team as Lead Full-Stack Developer & Project Manager. The project is designed around municipal maintenance and incident-reporting workflows; it is not an officially deployed city system. The engineering question that stayed with me was simple: how much should software claim to know?

### A flag is not a verdict

AC-CORE can flag a report as a possible duplicate when it has the same category as another report, was created within roughly the previous 24 hours, and is within about 50 meters. Those conditions make the reports worth comparing. They do not prove that both records describe the exact same physical issue.

The distinction matters. The system knows the category, approximate distance, and time. It may not know whether conditions changed between submissions, or whether one report includes useful detail the other does not. Automatically merging the records would turn a reasonable suspicion into a decision the available data cannot defend.

Instead, the system marks the new report as a possible duplicate. Both records remain available for review. An administrator can compare them and decide whether they refer to the same issue. The flag helps direct attention without removing information or pretending the system has reached a verdict.

This is a small design choice, but it changes how people interpret the result. When the evidence only supports suspicion, the interface should communicate suspicion rather than certainty.

### Context is different from prediction

Weather and elevation provide another example. AC-CORE polls and caches current Angeles City weather. If a report is inside a configured priority commercial zone and that cached state indicates rain, an explicit rule can raise its priority and severity. The rule adds context that may help an administrator decide what to review sooner.

For relevant active flooding and clogged-drain reports, the system can also compare nearby reports within roughly 500 meters and use elevation differences to show additional context. A nearby report at a lower elevation is a fact about two points in the data. It does not tell us how water will move between them.

The system can say: it is raining; this report is in a configured priority zone; a relevant report exists nearby at a lower elevation. Those observations may be useful together, but they do not establish that flooding will happen or that one report is objectively the most dangerous. AC-CORE uses distance and elevation as context for review, not as predictive hydrology.

### Boring rules are easier to explain

An explicit duplicate rule is not complicated: same category, within roughly 50 meters, within roughly 24 hours means possible duplicate. If someone asks why a report was flagged, the inputs and conditions can be inspected. The distance or time threshold can be tested, changed, and discussed with the people reviewing the reports.

The weather rule has the same quality. The cached state indicates rain, the report falls inside a configured zone, and the rule raises priority and severity. That makes it possible to debug an unexpected result and identify which condition produced it. It also makes disagreement useful: if an administrator thinks the threshold is too broad, the team can examine the rule rather than argue with an opaque score.

This is not an argument against machine learning or probabilistic systems. A prediction can be the right tool when the data and evaluation support it. The mechanism should match the evidence and the decision being asked of the user.

### What I learned

Before AC-CORE, I often assumed that adding more logic made a system more capable. Working through these decisions made me pay more attention to what the system did not know. A feature can be useful even when it only flags a case, ranks it for review, or adds context for a person to interpret.

That can be a more responsible result than turning incomplete evidence into a confident conclusion. It also gives the team something concrete to test and explain. The point is not to avoid useful automation; it is to be clear about what an automated result means and what it cannot establish.

Sometimes the better feature says less, but can explain exactly why it said it.
