AWS Academy taught me what services such as EC2, VPCs, IAM, load balancers, and Availability Zones were for. I completed the [Cloud Foundations coursework and badge](https://www.credly.com/badges/96846437-3bb4-48cd-95f2-a9b4540fb83e/public_url), and I could explain the basic purpose of each service. The harder part came when I had to reason about how they fit together.

For our final project in Cloud Computing (6CLOUDCOM), taught by [Dr. Jonilo Mababa](https://www.linkedin.com/in/jmababa/), our team designed an AWS architecture for a business case study. We chose Lazada Singapore Pte. Ltd. We modeled scalability, redundancy, and failure for the course; this was not work commissioned by Lazada or a representation of its production infrastructure. I valued the chance to study Cloud Computing under Dr. Mababa, whose emphasis on failure shaped how we approached the diagrams.

A diagram can look convincing while leaving basic questions unanswered. What happens if an application instance disappears? What if traffic grows? What if an Availability Zone becomes unavailable? And when one component is made redundant, which dependency becomes the next bottleneck?

### Knowing the pieces is not designing the system

Learning AWS services gave me vocabulary, but vocabulary is not architecture judgment. Knowing that EC2 provides compute, that a load balancer routes requests, or that an Auto Scaling Group adjusts capacity does not tell you which parts of a particular system need protection from failure.

The assignment pushed us to think about relationships. Where does a request go? Which components depend on one another? Where does state live? What happens to a request if a dependency is unavailable? A service diagram describes the pieces; the connections and assumptions between them determine how the system behaves.

That distinction changed how I approached our diagrams. Instead of adding services because they commonly appear in cloud architectures, we had to explain what each one was meant to do in our scenario. Architecture is about relationships between components, not just knowing the components themselves.

### Start asking what fails

Dr. Mababa emphasized thinking about failure instead of designing only for the happy path. Werner Vogels, CTO of Amazon, captured that idea in a line we returned to: “Everything fails, all the time.” The final project made us apply it to the diagrams. We moved past “How does the request reach the application?” and asked “What happens when this part stops working?”

For example, multiple application instances can reduce dependence on a single machine. A load balancer can route requests among targets it considers healthy. That does not make every failure disappear, but it gives the design a way to continue when one instance is unavailable.

Traffic growth raised a different question. An Auto Scaling Group can add or remove compute capacity according to configured metrics and policies. It is not a guarantee that capacity will appear instantly or that every spike will be handled perfectly. The policy, the time it takes to respond, and the rest of the architecture all matter.

We also considered distributing appropriate resources across Availability Zones. That can reduce dependence on one failure domain, but it does not guarantee zero downtime. A design still has to account for how traffic is routed, what state is shared, and which dependencies remain outside that distribution. Spreading instances across zones alone does not preserve every active session or make an application resilient by default.

### Redundancy needs a reason

It is easy to make a diagram more complicated by adding components associated with high availability. A load balancer, several instances, and multiple Availability Zones may look reassuring on a slide. Each addition also introduces behavior that someone has to understand and configure.

The more useful question is: what failure or constraint is this decision meant to handle? Why are there multiple instances? What happens to state if one disappears? Which dependency is still a single point of failure? What does the system do while capacity is changing?

Those questions do not always have one right answer. They do make it easier to evaluate whether a component belongs in the design, and to identify where the diagram is incomplete. Redundancy is useful when you understand which dependency it protects against and what assumptions remain.

### What I learned

Before the assignment, I thought of cloud design mostly as learning what each service could do. The work made me see that knowing the services is only a starting point. The harder task is tracing how a system behaves when a component fails, a dependency is unavailable, or a design assumption stops holding.

An architecture diagram should explain more than the happy path. It should make clear where requests go when everything works, and help answer what happens when something stops working. That is the difference between recognizing the pieces and reasoning about the system.
